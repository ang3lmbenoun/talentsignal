## Story
As a recruiter, I want to drop a real resume PDF (or paste a LinkedIn URL) and have
TalentSignal extract a candidate's name, skills, years of experience, and availability
automatically, so I don't have to retype what's already on the document.

## Slice
Backend parsing of an uploaded PDF (and/or a fetched LinkedIn profile) into the same
shape `POST /api/candidates` already accepts (`name`, `skills[]`, `experience`,
`availability`, `contactInfo`), wired to the existing drop zone on the Candidates
screen so a successful parse pre-fills the "Add manually" form instead of just showing
a toast.

## Why this was deferred, not built now
The S-25 Candidates redesign task explicitly asked for the drop zone to land visually
and functionally (accepts a drop, shows a toast) *without* real parsing, and named this
follow-up story as the place to track the parsing work itself: "Actual resume PDF
parsing is out of scope for this task — that's a separate story." The redesign shipped
`frontend/src/CandidatesScreen.tsx`'s prominent drop zone with the toast text "Parsed
preview — resume PDF parsing wiring coming in follow-up story," pointing here.

## Open questions for Ali before this can be scoped for real
- PDF parsing approach: a hosted extraction API, a local library (would need to pick
  one — nothing like this exists in the repo today), or a mocked-behind-an-adapter-seam
  provider matching the rest of this app's pattern (REQ-020's adapter-seam rule)?
- LinkedIn URL: scraping a public profile page has no sanctioned API without LinkedIn's
  own partnership program — needs a decision on whether this is in scope at all for the
  deadline, or whether "paste a LinkedIn URL" stays a visual affordance only.
- Confidence/redaction: the mockup's static preview labels itself "PII redacted" — does
  a real parse need the same redaction-then-reveal-on-role pattern the rest of the app
  uses for `contactInfo` (06_decisions/009)?
